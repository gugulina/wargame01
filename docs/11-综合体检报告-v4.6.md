## 0. 体检方法

| 手段 | 做了什么 | 得到什么 |
|---|---|---|
| 读代码 | 引擎 8,520 行、菜单页 575 行、工具链 2,000 行逐段过 | 结构与风险点定位 |
| 跑测试 | `npm test` 全绿 | 577 项断言基线 |
| V8 覆盖率 | `NODE_V8_COVERAGE` 分别跑 selftest / briefcheck+levelcheck / autoplay | **selftest 单支脚本按字节 90.7%，119/413 个函数块从未执行** |
| 真实浏览器 | `tools/shot.js` + CDP 注入探针（360×740 / 200% 缩放 / 注入载荷） | 渲染耗时、触控尺寸、注入是否真执行 |
| 对比度计算 | WCAG 相对亮度公式逐对算 | 3 处不达 AA |
| 静态扫描 | aria / role / focus / innerHTML / addEventListener / eval / 外部请求 | 见各条 |

**一句话结论**：机制与测试的底子是扎实的（577 项断言、23 条变异、钩子拦得住），
但**"数据可信"这个前提没建立起来**——存档被当成可信输入，一路拼进 `innerHTML`；
而唯一处理存档的界面（HQ）**一支脚本都没覆盖到**。这两件事叠在一起，是最该先修的。

## 一、P0 · 立即修（安全性 / 数据丢失）

### P0-1 存档导入可执行任意脚本（已实测复现）

| | |
|---|---|
| 位置 | `game/campaign.html`：`validateSave()` 4965–4979、`renderLog()` 7419、兵牌 `title` 6700、单位面板 7290、`ub-name` |
| 现象 | 把一份存档里的 `units[0].name` 改成 `"><img src=x onerror=...>`，`validateSave` **返回 ok:true**；页面渲染后脚本真的执行 |
| 实测 | 真实浏览器探针返回 `pwn1=1 pwn2=1 imgs=2`（单位名与战报两条通道都通） |
| 原因 | ① `validateSave` 只校验**类型与范围**（`type` 在不在 `TYPE` 里、`str` 是不是数字、坐标在不在界内），完全不看 `name` / `abbr` / `log[].text` / `log[].cls` 的内容；② 渲染层把这些字段当 HTML 拼（25 处 `innerHTML`） |
| 影响 | 玩家从群里拿到"我的存档"，双击导入即可在该页面执行任意脚本——可读 `localStorage` 里**所有**存档、进度，再悄悄导出。单机游戏没有账号，但"别人的档"这个入口是真实存在的 |
| 建议 | ① 渲染层收口：加 `esc()`（`& < > " '` 五个字符），**所有**插入模板的字符串过一遍，尤其 `title="`、`class="`、`innerHTML`；② 校验层补内容约束：`name`/`abbr` 限 1–40 字符且不含 `<>&"`，`log` 限 80 条、`text` 限 500 字符、`cls` 走白名单；③ 加断言：拿恶意存档跑一遍 `applySaveFile` + 渲染，断言 DOM 里无 `<img>`（`docs/10` 里 `hqSaveNote` 的做法可以照抄，但**要测真数据路径，不是测提示文案**） |
| 优先级 | **最高**。修完必须反向验证：把 `esc()` 撤掉，断言要红 |

> **为什么上次没发现**：`docs/10` 的 4.2 修的是"导入结果提示"那条通道（`hqSaveNote`），
> 修对了；但**数据本身**仍然长驱直入。这类"修了显示、没修数据"的缺口，
> 只有把载荷塞进真存档跑一遍才会露出来。

### P0-2 存档写入失败完全静默（进度会无声蒸发）

| | |
|---|---|
| 位置 | `saveGame()` 4917–4924；17 处调用点（3837 / 5202 / 5301 / 5410 / 5420 / 5437 … 5940） |
| 现象 | `saveGame()` 内 `try { localStorage.setItem(...) } catch { return false }`，**没有一处调用点看返回值** |
| 原因 | 早期把"存储失败"当成不需要处理的小概率事件；隐私模式与配额满（`QuotaExceededError`）实际都会走到这条 catch |
| 影响 | 隐私模式 / 磁盘满 / 浏览器清理策略下，玩家能打完整局，关掉标签页后**进度全丢且没有任何提示**。菜单页文案还写着"存档只写在本机浏览器里"，等于默认它一定写成功 |
| 建议 | ① `saveGame()` 失败时置 `state.saveBroken = true`，顶栏挂一个常驻「存档异常」胶囊，点开跳到 HQ 存档页并提示"请立即导出"；② 每次失败只弹一次 banner，不要每步都弹；③ HQ 存档页用 `navigator.storage.estimate()` 预估剩余空间 |
| 优先级 | 高。成本约 40 行，收益是"玩家不会白打一局" |

## 二、P1 · 该尽快修（覆盖盲区 / 兜底失效 / 可达性硬伤）

### P1-1 `renderHQ()` 零测试覆盖 —— 唯一的存档出入口没人测

| | |
|---|---|
| 位置 | `renderHQ()` 及其四个 tab（`hqDex` / `hqCards` / `hqSave` / `hqAide`） |
| 实测 | V8 覆盖率：selftest ✗、briefcheck+levelcheck ✗、autoplay ✗ —— **四支脚本没有一支执行过它** |
| 原因 | briefcheck 测存档路径时是**直接调 `hqSaveNote()`**（briefcheck.js:461–471），绕过了整个 HQ 的 DOM 构建与事件绑定 |
| 影响 | HQ 里放的是：导出/导入（唯一出入口）、配牌、副官问答。任何一处 DOM id 改错、tab 切换断掉、按钮没绑上，测试全绿而玩家点不动 |
| 建议 | briefcheck 加一节：`openHQ()` → 依次点四个 tab → 断言每个 tab 的容器非空、导出按钮存在、`#fileImport` 在 body 里、Esc 能关；顺带把 P0-1 的恶意存档从这里走一遍真实 UI 路径 |
| 优先级 | 高。这是"测试很多但关键面没测"的典型 |

### P1-2 全局错误兜底注册在脚本末尾，救不了启动期崩溃

| | |
|---|---|
| 位置 | `game/campaign.html:8306`（`window.addEventListener('error')`），全文 8,521 行 |
| 现象 | 监听器在**第 8306 行**才注册；此前 7,000 行顶层代码（含全部数据定义）已在执行 |
| 原因 | 兜底是后补的，就顺手写在了文件末尾 |
| 影响 | ① 任何**语法错误**（改关卡数据时最常见的失误）会让整段脚本不执行，监听器永远装不上；② 前 7,000 行的运行期错误同样逃逸 |
| 实测 | 故意在数据段插一个多余括号后加载：`errBar` 始终 `display:none`、`__WAR__` 为 `undefined`、`.hex` 数量 **0** —— 但静态骨架照常渲染：顶栏「岚口要地争夺战 / 第 1 / 12 回合 / 我方阶段」、图例、右侧空面板、甚至「结束我方阶段」按钮都在。**玩家看到的是一张空地图加一排点不动的按钮，没有任何报错** |
| 建议 | `<head>` 里放一个 10 行的独立 `<script>`：先装 `error` / `unhandledrejection`（只做 `msgEl.textContent` 与 `localStorage` 落盘，不依赖任何业务代码），再加一个 3 秒看门狗——若 `window.__WAR__` 仍未就绪，显示"加载失败，请刷新"。业务脚本里的那份监听可以保留，两份不冲突 |
| 优先级 | 高。成本 10 行，换掉"骨架在、棋盘空、无报错"这个最难排查的故障模式 |

### P1-3 `user-scalable=no` 禁掉了页面缩放（WCAG 1.4.4）

| | |
|---|---|
| 位置 | `game/campaign.html:5` `content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no, viewport-fit=cover"` |
| 现象 | 双指缩放被禁用，正文 13px、图例 10px、版本号 11px 全部不可放大 |
| 原因 | 棋盘自己实现了捏合缩放（`transform`），作者为避免手势冲突关掉了原生缩放 |
| 建议 | 去掉 `maximum-scale=1, user-scalable=no`，把手势冲突收窄到棋盘容器：`#boardView { touch-action: none }`（页面其余部分仍可原生缩放）。这是标准解法，不需要牺牲棋盘交互 |
| 优先级 | 高。低视力用户目前没有任何放大手段 |

| 位置 | 色值 | 对比度 | 用在哪 |
|---|---|---|---|

### P2-2 引擎零可访问性基建

| | |
|---|---|
| 实测 | `aria-*` **0 处**、`role` **0 处**、`tabindex` **0 处**、`:focus` 样式 **0 处**（菜单页各 1 处） |

## 六、做得好的地方（这些别在重构里弄丢）

1. **测试有真防线**。23 条变异测试全部命中，且历史上真抓到过 bug（崩溃收拢 +10 从未生效、`serve` 断言假绿）。这在本类项目里是少见的。
2. **数据与代码的一致性有机制**：`data/levels.js` 由引擎导出、`--check` 比对指纹、版本号单一真源。文档里那张兵种表也是生成的，不是手抄的。
3. **没有动态执行、没有外部请求、没有第三方运行时依赖**。`eval` 0 处、`fetch` 0 处（菜单页连 `fetch` 都刻意不用，注释写明了 `file://` 的原因）。双击即玩、断网可玩。
4. **注释写"为什么"而不是"改了什么"**，踩过的坑留在原地（例如 `docs/10` 里 `-1.`/`9 vs 9` 那类记录）。这直接降低了本次体检的沟通成本。
5. **破坏性操作有二次确认**（重开按钮），**错误条用了 `textContent`**（不会二次注入）。
6. **`LEVEL.pace` 这类"设计意图写进数据"**的做法，比任何口头约定都可靠。

**这一轮（v4.6.2）撞出来的坑，都写进代码注释了**：

| 坑 | 表现 |
|---|---|
| 同一 url 下有**两个 `<script>` 块** | `<head>` 的兜底脚本和引擎本体各有自己的 offset 空间。合成一份算，函数块从 426 变 834、行号报到 CSS 里、覆盖率从 90.3% 掉到 68.2%。按 `functions.length` 分组区分（引擎四百多、兜底三个） |
| V8 offset 是**相对脚本块**的 | 直接拿去换行号，会得到"第 2 行 `bar()`"这种假行号。加回脚本块在 HTML 里的起点才对 |
| `drop-shadow` 会把兵牌一起染色 | 第一版光标用 `filter: drop-shadow(...)`，结果蓝方兵牌被投上一层蓝边——兵牌本来就是蓝的，等于没画。改成 `::after` 的"白 2px + 蓝 3px"双层内描边（白边是必要的，纯蓝在蓝兵牌上完全看不出） |
| `stubEl` 缺 `removeAttribute` | 键盘光标要设 `aria-activedescendant`，selftest 的 stub 元素没这方法 → 引擎抛 `TypeError`，看着像引擎坏了，其实是假 DOM 不完整 |
| 「有没有 `.kbcur`」是假绿 | 只数元素个数的话，`kbMove` 忘了 `render()` 时旧格还留着，数量照样是 1。断言必须核到 `dataset.r/c` 等于当前光标坐标 |
