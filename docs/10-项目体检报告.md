## 1. 代码结构与规范一致性

### 现状概述

单文件架构下分层是清楚的：块注释用 `════ 章节 ════` 分隔（六角格数学 / 战斗判定 / 渲染 / 事件 / 存档 / HQ），数据（LEVELS、TYPE、TERRAIN、CRT、ASSETS、FORT）与逻辑分离，新增一关就是往 `LEVELS` 里加一项。

注释质量是本项目最值得肯定的地方——写的是"为什么"而不是"做了什么"，而且把踩过的坑写进去了。典型如 `game/campaign.html:2797`：

```js
/* 加守卫：剧情卡在无 DOM 的环境（自动化跑局、静态烘焙）里也要能安静播完。
   document.addEventListener 缺失时不该把整局炸掉，那只是一句对白。 */
```

这种注释在别的仓库里很少见，它省下的排障时间是实打实的。

### 发现的问题

**1.1 单文件已到 6,764 行，最长函数 210 行** — 中风险
- `boot` (L6555, 210 行)、`runAI` (L5058, 190 行)、`renderUnitBox` (L5673, 154 行)、`renderBoard` (L5272, 140 行)、`triggerMet` (L3551, 122 行)、`hqAide` (L6445, 109 行)
- `boot` 的长度其实无害（它是线性的路由配置），但 `runAI` 190 行意味着 AI 决策逻辑无法单独测试，改一处可能牵动全局。

**1.2 解锁规则有两份实现** — 中风险
- 引擎 `levelAccess()`（game/campaign.html:3890）
- 菜单页 `chainAccess() / access()`（index.html:411-429）
- 两份逻辑当前一致，靠 `levelcheck.js [9]` 逐关比对兜底。但"改规则要改两处"这件事没有任何机制强制——只有测试会告诉你忘了改，而测试是手跑的。

**1.3 缩进与风格没有机器约束** — 低风险
- 零 Tab 缩进（好），2 空格为主流，但有 193 行是奇数缩进（3/5/7 空格），来自对齐式续行。
- 没有 lint、没有 editorconfig、没有 prettier，风格一致性完全靠自觉。目前靠注释文化撑住了，但新人接手会立刻发散。

## 2. 依赖管理与版本风险

### 现状概述

游戏本体**零运行时依赖**——这是单文件架构最大的红利，没有 npm 供应链风险，没有 CDN 挂掉的风险，双击就能玩。仓库里也没有任何 `node_modules`。

### 发现的问题

**2.1 ~~没有 package.json~~ ✅ 已修（提交 `38b8b3d`）**
原问题：测试依赖装在项目外的 IDE 托管目录，靠 `NODE_PATH` 指向；jsdom 版本未锁定。
- `jsdom` 装在 `C:/Users/泽宇/.workbuddy/binaries/node/workspace/node_modules`，靠 `NODE_PATH` 环境变量指过去（README:314、316）。
- 三个后果：① 换一台机器 clone 下来测试全跑不起来；② IDE 升级或清缓存后依赖可能消失；③ **jsdom 版本没有锁定**，jsdom 升级改变 DOM 行为时，51 + 64 项断言可能集体静默失效或假绿，而你不会收到任何提示。

**2.2 Python 工具的三方依赖同样无清单** — 中风险
- `tools/audiostat.py`、`audioviz.py`、`sfxprep.py` 依赖 `numpy` + `miniaudio`，`audioviz.py` 还依赖 `matplotlib`。没有 `requirements.txt`。
- 这三个是音效选型的工具链，不是日常必需，但音效素材要重做时（BGM 4 首还没做）会用到。

**2.3 README 里写死了开发者个人绝对路径** — 中风险
- 3 处 `C:/Users/泽宇/.workbuddy/binaries/node/workspace/node_modules`（README:314、316 及相邻行）。这是"只有你自己能跑"的典型症状。

**2.4 Node 版本未声明** — 低风险
- 代码用了 async/await（23 处）、对象展开（59 处），但**没有**用可选链 `?.` 和空值合并 `??`（0 处）——说明作者有意保持了较宽的兼容面。这是加分项，但没有 `.nvmrc` 把这件事固定下来。

### 改进建议

| 优先级 | 动作 |
|---|---|
| **P0** | 加 `package.json`：`{ "devDependencies": { "jsdom": "^26.0.0" } }` + `"scripts": { "test": "node tools/selftest.js && node tools/check.js game/campaign.html && node tools/levelcheck.js && node tools/briefcheck.js && node tools/export-levels.js --check && node tools/orgcheck.js" }`。这样 `npm i && npm test` 一台新机器就能跑全套 |
| P1 | README 的 `NODE_PATH=...` 改成 `npm test`；保留一行说明"jsdom 是 devDependency" |
| P1 | 加 `requirements.txt`（numpy / miniaudio / matplotlib），或在这三个 py 文件头部注释里写明 |
| P2 | 加 `.nvmrc`（22） |

## 3. 测试覆盖率与质量

### 现状概述

**350 项断言（234 + 51 + 64）全绿**，另有 `check.js`（关卡数据静态校验）与 `orgcheck.js`（编制跨关一致性审计）。

这套测试里有几个设计是超出平均水平的：
- **`check.js` 校验每条事件 `when` 指向的兵牌/要点/编制是否真实存在** —— 事件写错 id 不报错、不崩溃，只会安静地永不触发。这条静态校验把"死事件"从运行时问题提前到校验期。
- **`autoplay-campaign.js` 跑完列出「从未触发」的事件** —— 实测确认当前 C3B 的 7 条事件触发率 36.5%–100%，零死事件。
- **`levelcheck [3]` 是防复发断言**：断言"引擎里不许再长出 `lvlList` / `startScreen`"，防止有人把已删的选关界面加回引擎。
- **`selftest.js:858-873` 覆盖存档导入的四条拒绝路径**（非本作文件 / 版本不符 / 关卡不存在 / 非 JSON）。

### 发现的问题

**3.1 三处"跳过即通过"的恒真断言，通过数含水分** — 中风险
- `tools/briefcheck.js:218` `ok('本关没有辎重队，跳过补给点气泡', true);`
- `tools/levelcheck.js:93` `ok('未制作的关不可进', true, '（已经没有占位关，跳过）');`
- `tools/levelcheck.js:121` `ok('第三关（非 open）在零进度下锁着', true, '（没有受锁的关，跳过）');`
- 这三条在"不适用"时直接算 pass。当前 350 项里约 3 项是水，比例不高，但趋势危险：以后再有人加"跳过即通过"，测试数字会越来越好看而覆盖面不变。

**3.2 无覆盖率工具，350 项覆盖的是导出的那一层** — 中风险
- 引擎 183 个函数，`window.__WAR__` 导出约 60 个。测试直接驱动的只有这 60 个；其余 120+ 个内部函数（渲染、HQ 面板、地形绘制、气泡定位）靠 DOM 断言间接覆盖。
- 目前没有工具能回答"哪些函数从未被执行过"。

**3.3 事件触发率有下限报告，但没有门禁** — 中风险
- 当前最低的"侦察营打光"触发率 36.5%。如果某次改动让它变成 0%，报表会显示 `0 0.0%`，**但测试不会变红**。死事件是靠人眼看的。
- 这与项目自己的约定（"每个事件都必须真的会触发"）有落差——约定靠自觉，不靠机器。

**3.4 测试不进 CI，全靠手跑** — 中风险
- 没有 `.github/workflows`。上一次提交时 `data/levels.js` 就差点带着旧版本提交（`--check` 抓出来的）。这类"忘了跑"只会越来越多。

**3.5 自战不可复现** — 低风险
- `autoplay-campaign.js` 无随机种子，200 局结果每次不同（C3B 这次 47.5%，记忆里上一轮记的是 57.5%）。做 A/B 平衡对比时会分不清"改动有效"还是"运气"。

### 改进建议

| 优先级 | 动作 |
|---|---|
| P1 | 恒真断言改成 `skip()`：单独计数、单独显示（`通过 60 · 跳过 2 · 失败 0`）。成本 10 行 |
| P1 | 给 `autoplay-campaign.js` 加触发率门禁：任一事件触发率 = 0 且该事件不是"稀有分支"，退出码非 0 |
| P1 | 加 `--seed` 参数（简单 LCG 替换 `Math.random`），让平衡对比可复现 |
| P2 | 接一次 `c8 --check-coverage` 或 `nyc` 看一眼真实覆盖率，先摸底再决定要不要设门槛 |
| P2 | CI（见第 8 节） |

## 4. 潜在安全漏洞

### 现状概述

正面清单先列出来，这一项做得比多数个人项目好：**无 `eval`、无 `new Function`、无 `fetch`、无外链 `<script src>`、无第三方 CDN、无内联事件属性**。攻击面主要就一条：存档文件导入。

### 发现的问题

**4.1 存档导入 XSS（可传播）** — **高风险** ✅ **已修，并已补上真防线**

链路三步，全部成立：

① `game/campaign.html:3956-3963`，`applySaveFile()` 的版本校验分支：
```js
if (pack.v !== SAVE_VER) {
  return { ok: false, msg: '存档版本不符：文件是 v' + pack.v + '，本作是 v' + SAVE_VER + '，无法读取。' };
}
```
`SAVE_VER = 3`（L3765）。`pack.v` 来自用户 JSON，**类型不受约束**——`!==` 对任何非数字都成立，所以 `pack.v` 可以是任意字符串。

② msg 流向 `hqSaveNote()`，`game/campaign.html:6441`：
```js
el.innerHTML = '<b style="color:' + (ok ? '#2F7D4F' : '#A83A3A') + '">' + msg + '</b>';
```

③ 构造一个 `.json`：`{ "app":"cangyu-wargame", "kind":"save", "v":"<img src=x onerror=...>" }`，受害者导入即执行。

**为什么定级为高而不是"自 XSS 无所谓"**：导出/导入存档是本作的一等功能（README 有专门一节、HQ 有独立存档页、菜单页有常驻"存档管理"入口）。这意味着**存档文件会在玩家之间传播**——"自 XSS"在这个语境下是可传播的。

现有测试为什么没抓到：`selftest.js:867` 只断言 `applySaveFile({...v:999}).ok === false`，**从不检查 msg 的内容**。

**修复（一行）**：
```js
function hqSaveNote(msg, ok) {
  const el = document.getElementById('hqSaveNote');
  if (!el) return;
  el.textContent = msg;                       // 不再拼 HTML
  el.style.color = ok ? '#2F7D4F' : '#A83A3A';
  ...
}
```
再补一条断言：`selftest` 里对 `v: '<img src=x onerror=alert(1)>'` 断言返回的 `msg` 不含 `<`。

> **本次同步补充（重要）：上面那条断言是假防线，已换成真的。**
> `38b8b3d` 按建议加了 `textContent`，也加了 selftest 断言——但那一条断言的是
> `applySaveFile` 返回的 `msg` 不含 `<b`。问题是 **msg 里从来就不会有 `<b>`**
> （那个标签是渲染端拼的），所以断言恒真：哪天有人把 `hqSaveNote` 改回 `innerHTML`，
> selftest 依然全绿，漏洞照样复活。
>
> 已在本次同步里修正：
> 1. `hqSaveNote` 纳入 `window.__WAR__` 导出（注释写明为什么要导出）；
> 2. `tools/briefcheck.js [12]` 新增两条断言——在 jsdom 真 DOM 里调用
>    `hqSaveNote('<img src=x onerror=alert(1)>')`，断言元素 `innerHTML` 里
>    **不含 `<img` 且含 `&lt;img`**（即靠转义而非删除）。
>
> **已做反向验证**：临时把 `textContent` 改回 `innerHTML` 跑一次，断言如期变红
> （失败 2 项，且报错里能看见 `<img src="x" onerror="alert(1)">` 真被写进 DOM），
> 改回后恢复 64 项全绿。这条断言是真会响的。
> briefcheck 项数 62 → **64**。

**4.2 导入路径的存档内容校验弱于本地读档** — 中风险
- `readSave()`（L3983-3997）做了四道校验：关卡存在且已制作、版本匹配、`map` 长度匹配关卡行数、`units` 非空数组。写得很扎实。
- 但导入路径 `applySaveFile()` 只校验了 `v` 和 `lv`，**没走 `readSave()` 那套**。`pack.save` 被直接 `JSON.stringify` 写进 localStorage，下次 `restoreGame()` 会把它整个接过来（`JSON.parse(JSON.stringify(s.units))`），兵牌字段一个都不校验。
- 篡改的存档能造出异常战力、`NaN`、不存在的 `corps`，游戏不崩但状态被污染。

**4.3 无 CSP、无全局错误兜底** — 中风险（打包后升为高，见第 6 节）

**4.4 localStorage 明文存档，玩家可自行改分** — 低风险
- 单机兵棋，改分只坑自己。可接受，不建议投入。

### 改进建议

| 优先级 | 动作 |
|---|---|
| **P0** | 4.1：`hqSaveNote` 改 `textContent` + 补断言 |
| P1 | 4.2：把 `readSave()` 的那套校验抽成 `validateSave(s)`，导入路径也过一遍；顺带把"校验通过才写入 localStorage"做成原子操作 |
| P2 | 4.3：加 `<meta http-equiv="Content-Security-Policy">`（打包时尤其值得，能顺手堵住 file:// 下的一类问题） |

## 5. 性能瓶颈

### 现状概述

**必须先说清楚：这一节是本报告里实测依据最少的一节。** 没有真机 profiling、没有低端机实测、没有长时间游玩的内存曲线。以下结论来自代码结构与一次间接计时。

### 发现的问题

**5.1 渲染是全量重建，不是增量更新** — 中风险
- `render()` 一次调六个子渲染：`renderBoard` / `renderHUD` / `renderGoal` / `renderUnitBox` / `renderLog` / `syncUnitOps`。
- `renderBoard` (L5272) 拼完整段 HTML 后 `board.innerHTML = html`（L5390）。全项目 32 处调用 `render()`，**每次点击都重建一遍**。
- 最大关卡 C3：280 个六角格 + 48 个兵牌 ≈ 330 个节点，每个格子带地形类、控制态类、工事类、可达态类。桌面浏览器单次大概几毫秒，**这是"能跑"而不是"没问题"**。
- 真正的代价是副作用：全量换 `innerHTML` 会丢掉焦点、CSS 动画状态、滚动位置。代码里 `syncUnitOps` 被刻意放在最后（注释写明"气泡要等 renderBoard 把 DOM 换完才能定位"），说明作者已经踩过这个坑——但它是用"约定顺序"解决的，不是用机制解决的。

**5.2 规则层性能不是瓶颈（有实测）** — 低风险
- 200 局自战耗时 125 秒 ≈ **0.62 秒/局**（vm 沙箱，无 DOM）。规则判定 + AI 决策的量级远小于一帧预算。优化该冲渲染，不该冲算法。

**5.3 打包前没做过真机实测** — 中风险
- `fitView` / 缩放 / 触摸（L5955 `touchDist` 87 行）都只在桌面验证过。兵棋是格子密集的 UI，低端安卓上最容易翻车。

**5.4 素材体积有 480 KB 死重量** — 低风险
- `game/assets/sfx/prev/` 136 KB（5 个上一版音效，代码零引用）
- `game/audio-lab/` 344 KB（15 个候选音效 + 对比页，代码零引用；`docs/08` 里有说明它是选型工具）
- 两者都还有历史价值，但没必要留在主仓库 HEAD。

**5.5 无障碍：`user-scalable=no`** — 低风险（合规）
- `game/campaign.html:5`：`maximum-scale=1, user-scalable=no`。违反 WCAG 1.4.4，且兵棋恰恰是最需要放大的 UI（格子小、字号小）。项目自己实现了 `fitView` 缩放，所以禁掉系统缩放的理由不成立。

### 改进建议

| 优先级 | 动作 |
|---|---|
| P1 | 打包前做一次真机实测（低端安卓 + 手机 Safari 各 30 分钟），重点看 C3（280 格）连续操作 20 回合的帧率与内存 |
| P2 | `renderBoard` 改增量：地形层（静态）只在切关时建一次，之后只改 `class`。这一改能同时解决 5.1 的副作用问题 |
| P2 | 移除 `user-scalable=no`（保留 `maximum-scale=5`） |
| P2 | `prev/` 与 `audio-lab/` 移出 HEAD（git 历史里留着即可），或加进 README 的"历史素材"说明 |

## 6. 错误处理与日志

### 现状概述

### 发现的问题

（`game/campaign.html:6660` / `:6668`），捕获后显示页面错误条并把诊断写进
`localStorage['cangyu.lasterr']`。打包的前置条件已经满足。

## 8. 可维护性与可扩展性

### 现状概述

**扩展性是这个项目的强项**，而且是有意识设计出来的：
- 关卡 = `LEVELS` 数组里的一项；胜利条件三种（`score`/`survive`/`reach`）由 `win` 对象驱动，加第四种只需在 `checkEnd` 加一个分支。
- 事件 = 数据表（`when` + `effects`），14 种触发器、5 种效果，加新触发器只动 `triggerMet` 一处。
- 剧本 = `LEVEL.story` 驱动，改剧本不碰 HTML。
- 素材 = `ASSETS` 槽位（部分有效，见 7.3）。

### 发现的问题

**8.1 ~~`data/levels.js` 的一致性靠人工跑 `--check`~~ ✅ 已修**：pre-commit hook 已加
（`.git/hooks/pre-commit`），改动 `game/campaign.html` 时自动跑 `export-levels.js --check`
+ `check.js`。这是本次修复里性价比最高的一条——它把"忘了导快照"这一整类问题变成了不可能。
- 快照由 `tools/export-levels.js` 生成，用 `--check` 校验是否走样。
- **本次提交前就抓到一次不一致**：`verTag` 从开始页页脚挪到顶栏之后忘了重新导出，快照停在旧版本。是 `--check` 发现的，不是人发现的，但 `--check` 也是人手动跑的。
- 没有 pre-commit、没有 CI，这条唯一的一致性守卫全靠记性。

**8.2 版本号有三个来源** — 中风险
- `game/campaign.html:925` `<span id="verTag">v4.3</span>`（HTML）
- `game/campaign.html:3765` `const SAVE_VER = 3;`（存档格式版本，与展示版本是两回事，但命名容易混）
- README 里的版本标题（已落后）
- 三者无关联机制。

**8.3 183 个函数全在全局作用域** — 中风险
- 单文件无模块系统，`state` / `LEVEL` 是可变全局。目前靠 `__WAR__` 的 getter 暴露给测试（`get LEVEL()` 而非值拷贝，注释里写明原因），设计上是清醒的。但随着关卡增加（正篇 12 关只做了 3 关），全局命名冲突的风险线性上升。

**8.4 解锁规则两份（同 1.2）** — 中风险

**8.5 打包未验证** — 中风险
- 好消息：路径全是相对路径，代码不用改。
- 坏消息：从没打过。`file://` 下的行为（已有一条针对性设计：不用 fetch 用 `<script src>`）、窗口尺寸变化、无 F5 的后果——这些都是"打完才知道"。
