## 二、四处缺陷

### P1-1 · 撤销爆破不退装药

`doDemolish` 里扣装药排在 `pushUndo()` 之前：

```js
u.charges -= 1;     // ← 先扣
pushUndo();         // ← 后快照：快照里存的是"已经扣过"的账
```

撤销恢复的是快照，于是桥的耐久回来了、装药没回来。实测 `5 → 4 → 撤销后仍是 4`。

**为什么后果比看起来重**：C7B 一共 10 份装药，炸四座要 8 份，容错只有 2 份。
误点两下撤销，达成线就打不满了；而兵牌面板**不显示装药**，
只有按钮上那个"剩 N 份"。玩家不会把"后来炸不动"和"刚才撤销过一次"联系起来。

对照组：`doAttack` 一直是先 `pushUndo()` 再扣弹药，所以只有爆破这一处踩了。

修法：装药检查留在快照之前（装药为 0 不该压栈），扣减挪到快照之后。

### P1-2 · 桥被修通不播报

```js
if (before <= 0 && w.hp >= w.maxHp) {   // ← 只有"一次修满"才播报
```

C7B 的桥是 `hp 2 / repair 1`，要修两回合。第 2 回合 `before = 1`，
条件不成立，走的是 `else if (w.hp > 0)` → "敌军工兵正在抢修（2 / 2）"。
**桥通了，但没有横幅、没有"这一处白炸了"。**

玩家在断桥上补射一发、以为还断着，天亮结算发现只断了两座判负——
而战报里找不到任何一句提示。这正是 `docs/04` §十七 里写的
"炸完还得守"的反面：守没守住，玩家不知道。

修法：判据改成"这一次把耐久补满"（`before < maxHp && hp >= maxHp`），
repair 大于等于 maxHp 的一次性修通照样命中。

### P2 · 护送关结算面板走错分支

结算面板按 `win.kind` 分四支：`reach` / `demolish` / `survive` / 其余走积分。
v5.1 新加的 `escort` 没跟进来，掉进最后的积分分支：

```
要点得分  0 / undefined 分
```

而护送关的 `winScore` 本来就没定义，这一关也根本不算分。

**这是"加了一种胜负类型"时的典型漏改**。五种 `kind` 要同时改四个渲染口：

| 渲染口 | reach | escort | demolish | survive | 备注 |
|---|---|---|---|---|---|
| `renderGoal`（右栏目标） | ✓ | ✓ | ✓ | ✓ | |
| 结算面板 `#mStats` | ✓ | **✗ → 已补** | ✓ | ✓ | 这一处不在任何断言里 |
| `judgeFinal`（终局判定） | ✓ | ✓ | ✓ | ✓ | |
| `perfectHint`（超额提示） | ✓ | ✓ | ✓ | ✓ | |

修法：补 escort 分支，写"车队撤出 X 支（达成 3 · 满员 5）"+"车队在路上 N 支"。

### P3 · 半损的桥写成"完好 1 / 2"

```js
workDown(x) ? '已炸断' : '完好 ' + x.hp + ' / ' + x.maxHp
```

`hp 1 / maxHp 2` 时输出"完好 1 / 2"——完好就是没动过，掉了一半是受损。
这一栏是玩家判断"要不要回头补一发"的唯一依据。

修法：三档分开写（已炸断 / 完好 / 受损 N / M）。

## 四、记下来没改的

**1. 四个超长函数**：`renderUnitBox` 263 行、`renderBoard` 233、`doAttack` 197、`runAI` 271。
都能拆，但拆的收益是"以后好改"，成本是"现在可能改坏"——而它们各自被几十条断言和
自战盯着。等真需要动它们的时候再拆，不为拆而拆。

**2. `cov.js` 的口径**：不跑自战，所以 `aiRepairGoal` / `aiGuardWork` 这类
只在 AI 回合执行的函数永远显示"从未执行"。数字偏残，别拿它当覆盖率结论。
（工具自己也会打一行"8 份引擎覆盖没合进来"。）

**3. 破袭关的超额判据对增援不健壮**：`judgeFinal` 里
`alive('blue').length >= startN - 3`，`startN` 只数 `wave === 1`，
而 `alive` 包含后来的增援。C7B 蓝方没有增援，所以现在没事；
以后给破袭关加增援，这条会变成"永远满足"。
